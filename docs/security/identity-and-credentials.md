# Identity and credentials

Product transport identities are persisted libp2p Ed25519 keypairs. Missing identities are fatal unless explicit onboarding enables creation. Back up the identity file only through an encrypted operator-controlled channel and restore it before replacing a host; preserving it preserves the PeerId. Pin distribution must include the complete terminal `/p2p/<exchange-peer>` address, and transport-key replacement requires redistributing all pins before restart. Secret files are bounded, regular files with no group/other permissions; private material is never emitted in diagnostics.

Clients and servers pin the exchange `PeerId` and validate every configured exchange address against that pin before authentication. Each address must contain exactly one terminal `/p2p/<exchange-peer>` component; missing, middle, duplicate, or conflicting components are rejected. A pin mismatch must close the connection without reading or sending a credential. Product mode supports a bounded validated address list and rotates through it deterministically after failed dials using capped exponential backoff with OS-random jitter. The authenticated control owner retains readiness while any admitted exchange connection remains, emits readiness loss after the final connection closes, and emits a higher readiness generation only after fresh Authenticate/Ping recovery.

Peer credentials use `p2x1.<credential-id>.<base64url-secret>`. The secret is 32 bytes of OS-generated entropy. The exchange stores only the domain-separated SHA-256 digest and binds it to peer, tenant, role, scopes, quota, and validity. Unknown IDs, wrong secrets, revoked credentials, expired credentials, and peer mismatches use the same public invalid-credential code.

Rotate by adding a second credential, deploying it, observing successful re-authentication, then revoking/removing the old credential at a strictly higher authorization revision. Snapshot replacement rejects decreased revisions and same-revision binding changes; an identical snapshot is idempotent. Replacement returns `PrincipalRevoked` and `ClosePeerConnections` for every affected session, with the current exchange `ConnectionId` set available to the owner. Revocation invalidates new control work and sessions, removes relay admission and server registry ownership before closing admitted exchange connections, and does not promise recall of already active direct streams. Authenticated relay admission fails closed for missing, expired, revoked, role-incompatible, scope-incompatible, unsupported-profile, or draining sessions. Verification-key YAML is public-key-only, bounded, strict, and uses activation/retirement windows; the ticket signing seed remains in its separate 0600 secret file. The exchange transport Ed25519 public key and ticket signing public key must differ; startup rejects equal keys. Secret reads validate the opened descriptor and read through a hard limit, and failed atomic writes clean temporary files. Ticket claims are constructed through a validated API, raw tickets are bounded/redacted wrappers, and key-ring verification selects one exact active key by envelope key ID before checking all bindings and time windows. Product servers require `--ticket-verification-keys-file` and load the strict public verification ring before networking. A verified ticket is consumed once by ticket ID and retained through expiry plus five seconds by default; configurable proxy skew is bounded to 30 seconds and live replay entries are never evicted. Immutable envelope/signature/time verification runs in a bounded server worker; current auth, service, registration, authorization revision, and replay consumption remain in the single server owner. Revocation stops new issuance and current registration rechecks invalidate stale tickets, but cannot recall an already authorized active stream. Local resolution tests cover binding failure without replay consumption, expiry-plus-skew retention, and replay rejection. Phase 4 rechecks ticket time at the owner transition and preflights global/per-client/per-service/upstream-dial capacity before reserving stream state and consuming a ticket. Stream-ID collisions preserve the existing admission entry, consume the presented ticket once, and reject its replay without allocating a replacement ID. A refusal or timeout remains consumed, while capacity failure leaves replay state untouched. Fixed TCP ingress accepts only server-configured IP-literal `SocketAddr` destinations. The destination is absent from advertisements, service-set hashes, ticket claims, wire messages, lifecycle output, and public error text; lifecycle records contain stable codes, hashes, counts, and byte totals only. The raw TCP process gate scans each run's exact generated selector, upstream, credential, ticket/session, address, and payload markers rather than unrelated constants.
